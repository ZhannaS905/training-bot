# FitPP → Training Test: уведомления, этап 1 (только предпросмотр)

Этот кандидат создан отдельно от работающего бота. **Ни один файл запуска
`bot.js`, `bothost-test.cjs`, `direct-training-test.cjs` или логика опросов не менялись.**

## Подтверждено ранее оператором

- BotHost Training Test: Node.js 22.23.4.
- Переменные `FIREBASE_API_KEY`, `FIREBASE_BOT_EMAIL`, `FIREBASE_BOT_PASSWORD` присутствуют.
- Ручной Firebase Auth + Firestore REST GET документа
  `fitppTestWorkspaces/synthetic-v1/states/main` в проекте `fitpp-test`
  завершился `READ_OK`.
- Результат `READ_OK` не доказывает, что документ уведомлений доступен
  и что будущая операция будет корректно обнаружена.

## Реализация

- `src/fitpp-notification-dry-run.cjs` — чистая функция сравнения двух
  снимков состояния. Обнаруживает **новую** операцию `attended` в `visitOps`,
  сверяет `visits`, `subscriptionId` и уменьшение `left` ровно на 1.
  Для тестового клиента требуется явно разрешённая привязка
  `notificationBindings/training-test` с нужным botId.
- `fitpp-notification-preview.cjs` — **отдельная команда**: Firebase
  Email/Password Auth, два Firestore REST GET, безопасный вывод без токенов,
  идентификаторов получателя, телефонов и имён. Запись в Firestore и запросы
  к MAX в коде отсутствуют. Первый снимок всегда считается исходным.
- `test/fitpp-notification-dry-run.test.js` — тесты детектора и декодера.
  Тесты добавлены, но их успешное выполнение должно быть подтверждено
  отдельно перед использованием.

Команда проверки исходного состояния (после отдельного согласования
развёртывания кандидата в изолированную среду):

```sh
node fitpp-notification-preview.cjs
```

Ожидаемое сообщение: `FITPP_DRY_RUN_BASELINE_OK`. Это **не** уведомление.

Только при явно разрешённом отдельном тесте, в консоли без второго
экземпляра бота и с контролем остановки:

```sh
node fitpp-notification-preview.cjs --watch
```

Команда делает GET каждые 30 секунд и печатает `FITPP_PREVIEW_ONLY remaining=N`
при подходящем изменении между снимками. Она не отправляет сообщений.
Если нет прав чтения привязки, завершится безопасной ошибкой
`FITPP_DRY_RUN_FAILED HTTP_403`.

## Ограничения и защита от ложных уведомлений

1. Первый снимок — только baseline. Операции, уже существовавшие до
   запуска, не уведомляются.
2. Несколько списаний одного абонемента между двумя чтениями считаются
   неоднозначными и пропускаются; это консервативный пилот.
3. Сравнение двух снимков без устойчивой очереди не даёт гарантий доставки,
   не переживает пропуск промежуточных состояний и **не является готовой
   системой автоматических уведомлений**.
4. В реальном отправителе понадобятся долговременная очередь,
   защита от повторной доставки по `operationId`, обработка отмен и
   неопределённого результата MAX API. Нельзя автоматически повторять
   отправку после тайм-аута MAX без сверки.
5. Firebase пользователь этого пилота обладает правами записи по
   существующим правилам. Команда программно использует только GET,
   но для постоянного решения нужны отдельные минимальные права.
6. **Нельзя** запускать этот кандидат в рабочем MAX-боте, объединять
   с `main` или включать отправку без отдельного разрешения.
7. Если `notificationsEnabled=false`, предпросмотра не будет.

Проверка перед любым деплоем: ревью diff, `node --test
test/fitpp-notification-dry-run.test.js`, затем полный `npm test`;
проверить текущую конфигурацию BotHost и то, что кандидат не заменяет
действующий entrypoint. Ни одно развёртывание этим PR не выполняется.
