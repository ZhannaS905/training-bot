# Training Test: собственный Dockerfile с Node.js 22

Профиль предназначен только для `refactor/cleanup-training-bot`. Публикация
кода не означает сборку или развёртывание на BotHost. Основной бот и main не затрагиваются.

## Что объясняют предоставленные логи

- Node.js 20.20.2 не соответствует `engines.node >=22`. Dockerfile использует
  `node:22-bookworm-slim` и проверяет major=22 при сборке; тестовый запуск
  дополнительно отвергает любой Node ниже 22.
- Созданный при сборке `/app/http-wrapper.js` может быть скрыт монтированием
  `/app` при старте. Это соответствует описанному BotHost случаю исчезновения
  артефактов образа. Без полного журнала и фактических mounts конкретного
  контейнера это объяснение остаётся обоснованным предположением.
- Отказ bothost-test.cjs — отдельный результат защитных проверок. Смена Node и
  устранение wrapper не отменяют требований к токену, личности, чату и данным.
  По одному прежнему общему сообщению нельзя установить, какое поле неверно.

Официальные источники:
- https://bothost.ru/docs/custom-dockerfile
- https://bothost.ru/docs/common-errors
- https://bothost.ru/docs/main-file-entrypoint

## Расположение файлов и команда запуска

| Назначение | Путь в контейнере |
|---|---|
| Код | /opt/training-test |
| Точка входа | /opt/training-test/bothost-test.cjs |
| Публичный дополнительный CA | /opt/training-test/certs/russian-trusted-root-ca.pem |
| Ожидаемое состояние | /app/data/training-test/live/state.json |
| Архив ускоренного теста | /app/data/training-test/archive/accelerated-cleanup/ |

CMD: `node /opt/training-test/bothost-test.cjs`. Автоматическая HTTP-обёртка и
`npm start` не используются. Сервер `/health` и `/webhook` предоставляет сам
профиль. Рабочий каталог `/opt/training-test` не зависит от содержимого `/app`.
Включён непривилегированный пользователь `node` (UID/GID 1000:1000 в образе).

Dockerfile копирует только перечисленные файлы профиля и его зависимости.
`.dockerignore` также построен как разрешающий список. `.env`, тестовые состояния,
логи, архивы голосования, токены и secret в контекст/образ не включаются.
Сценарии npm при установке отключены. У проекта сейчас нет внешних зависимостей.
Существующий lockfile сохранён; код обычного бота в образ не копируется.

## Защиты и диагностика

Все прежние ограничения действуют: фиксированный тестовый чат, проверенный
числовой ID/username/is_bot через MAX до слушателя, запрет API-записей и событий,
AUTO_PUBLISH=false, проверка SHA-256/истории состояния и эксклюзивная блокировка.
При отсутствии ожидаемого state.json приложение отказывает, а не создаёт новый.
Никаких автоматических миграций, очистки состояния или снятия чужой `.lock` нет.
Политика рестартов BotHost не задаётся Dockerfile и остаётся отдельным вопросом
настройки платформы; образ не превращает отказ в бесконечный цикл ожидания.

Новые журналы показывают только разрешённый код причины, например:

| Код | Проверить без ослабления защиты |
|---|---|
| NODE_VERSION_REQUIRED | Фактический Node; используется ли собственный образ |
| TEST_CONFIG / TEST_BIND | BOT_MODE=test, точный CHAT_IDS, PORT=3000, HOST=0.0.0.0 |
| TOKEN_CONFLICT | BOT_TOKEN отсутствует либо равен TEST_BOT_TOKEN |
| TEST_TOKEN_REQUIRED | Тестовый токен введён в секретных настройках |
| WEBHOOK_SECRET_REQUIRED | Secret имеет допустимый формат, без пробелов |
| EXPECTED_ID_REQUIRED | Подтверждённый числовой ID задан корректно |
| EXPECTED_STATE_REQUIRED / STATE_HASH_REFUSED | Хеш согласованного state.json, не случайного файла |
| TEST_IDENTITY_REFUSED / TEST_CHAT_REFUSED | Именно Training Test и разрешённый чат |
| UNEXPECTED_CA / TLS_REQUIRED | Корректный CA-путь и включённая проверка TLS |
| NODE_PRELOAD_REFUSED | Нет NODE_OPTIONS с дополнительной обёрткой/предзагрузкой |
| MAX HTTP 401 | Токен не принят MAX; не заменять его рабочим токеном |
| STARTUP_REFUSED | Нужна отдельная безопасная диагностика; сырое исключение скрыто |

Неизвестные исключения, пути с данными и ответы API не выводятся.

## Настройки после отдельного разрешения на развёртывание

Только в отдельном Training Test выбрать «Использовать собственный Dockerfile».
Dockerfile лежит в корне репозитория. Ветка — `refactor/cleanup-training-bot`;
язык — Node.js; порт — 3000; домен включён; кастомный домен пустой.
Поле главного файла можно оставить `bothost-test.cjs`, но при собственном
Dockerfile реальную команду определяет CMD. Не задавать `/app/http-wrapper.js`.
Если платформа продолжает навязывать такую команду, остановиться и уточнить
поведение у BotHost вместо отключения проверок или редактирования wrapper.

Переменные — по `bothost-test.env.example`. Dockerfile задаёт безопасные
несекретные значения по умолчанию. Секреты, подтверждённый ID и контрольная сумма
по-прежнему обязательны и не встраиваются в образ. Если в панели уже задан
NODE_EXTRA_CA_CERTS со старым `/app/certs/...`, его нужно согласованно убрать
либо заменить на `/opt/training-test/certs/russian-trusted-root-ca.pem`.
Иначе защита правильно откажет. Не отключать проверку TLS и не добавлять NODE_OPTIONS.

Данные остаются в постоянном хранилище BotHost `/app/data`, отдельно от кода.
Не менять их ради прохождения проверок. Для пользователя `node` должны быть
доступны чтение согласованного state.json и создание собственной `.lock`.
Подготовить владельца UID/GID 1000:1000 и права только на каталог НОВОГО тестового
экземпляра: каталоги 700, файлы 600. Не выполнять chmod 777, рекурсивную смену
прав рабочего бота или копирование пустого state.json. Монтирование может
заменить права, заданные при сборке; фактическое хранилище проверяется отдельно.

## Как безопасно проверить

1. Офлайн: `node --test test/bothost-docker.test.js test/bothost.test.js`.
   Проверяет Node 20/22, состав контекста, зависимости, запуск кода вне `/app`,
   переносимый путь CA и все защитные проверки с заглушками MAX.
2. После отдельного разрешения и при наличии локального Docker собрать образ:
   `docker build --pull -t training-test-bothost:node22 .`.
   Секреты и реальные состояния не передавать как build args или build secrets.
3. Не запуская приложение, проверить версию в образе:
   `docker run --rm --network none --entrypoint node training-test-bothost:node22 --version`.
   Должна быть версия v22.x. Проверить наличие /opt/training-test/bothost-test.cjs
   и публичного сертификата в образе. Это ещё не проверка доступа MAX.
4. Для проверки, что `/app` не скрывает код, запустить образ без сети и без
   токенов с отдельной пустой тестовой папкой, примонтированной в `/app`.
   Ожидается безопасный отказ TEST_TOKEN_REQUIRED, а не MODULE_NOT_FOUND.
   Не монтировать production, реальные состояния или каталоги рабочего бота.
5. Приёмка реального MAX и настоящего состояния — только после следующего
   разрешения: сверить хеш, владельца/права и политику рестартов нового экземпляра,
   затем один запуск. Не переключать webhook в рамках проверки сборки.

Локально Docker не обнаружен, поэтому фактическая сборка образа и поведение
монтирования BotHost здесь не проверялись. Офлайн-модель размещения файлов
не является Docker-сборкой или развёртыванием.
