# Ручной тестовый опрос

Только `refactor/cleanup-training-bot`, memory Training Test, группа MAX
`-80345864298680` («Тест тренировок»). Production и Amvera не настраивать.

Администратор из `TEST_ADMIN_IDS` отправляет `/тестопрос` или
`/тестопрос 2026-10-24` в тестовую группу. Без даты выбирается ближайшая
ещё не начавшаяся тренировка по МСК: 23 октября 2026 это 24 октября,
18:00, онлайн. Явная дата строго YYYY-MM-DD, существующая, не пятница,
не прошедшая и с ещё не наступившим временем начала. Неверная команда
ничего не отправляет. Без TEST_ADMIN_IDS команда отключена; ID не угадывать.

## Подготовка оператором (код сам настройки не меняет)

1. Проверить отдельные тестовые токен, `TEST_EXPECTED_BOT_ID`, секрет webhook,
   `BOT_MODE=test`, `CHAT_IDS=-80345864298680`. Остаются обязательными проверки
   личности бота, названия группы и членства.
2. Получить проверенный числовой MAX user_id администратора. Настроить
   `TEST_ADMIN_IDS` (несколько через запятую). Имя/username не подходят.
3. Подключить постоянный том, сохраняющийся при перезапусках **и пересоздании
   контейнера**, с надёжными fsync и эксклюзивным созданием файлов.
   Задать абсолютный `TEST_ATTEMPT_DIR` в нём. Каталог должен быть доступен
   пользователю `node`, закрыт от посторонней записи и выделен только этому боту.
   Если BotHost не гарантирует такой том, ручную отправку не включать.
4. Только при первом вводе нового хранилища создать в каталоге два файла:
   `scope` с единственной строкой `training-test:-80345864298680:<проверенный TEST_EXPECTED_BOT_ID>`
   и пустой `attempts.jsonl`. Угловые скобки заменить реальным ID.
   Обеспечить сохранение файлов/каталога на томе перед включением отправки.
   Никогда не обнулять существующий журнал при деплое или рестарте.
5. Оставить `AUTO_PUBLISH=false`. Для ручной публикации оператор включает
   `TEST_ALLOW_SEND=true`. Для обновления списка имён нужен `TEST_ALLOW_EDIT=true`,
   для удаления в 22:00 МСК даты тренировки — `TEST_ALLOW_DELETE=true`.
   Эти разрешения сами отправку не запускают.
6. Убедиться, что тестовый webhook доставляет `message_created` и
   `message_callback` с существующей проверкой секрета. Затем администратор
   может отправить команду сам. В рамках этой разработки отправок не было.

## Устойчивость и ограничения

До запроса MAX под эксклюзивной блокировкой записывается и fsync-ится только
дата попытки и SHA-256 идентификатора командного события (с областью бота/чата).
Это не журнал сообщений: текста команды, ID администратора, голосов, имён,
message_id отправленного опроса и истории изменений на диске нет.
На одну дату допускается одна попытка, включая автоматическую публикацию,
если оператор когда-либо отдельно включит её. Повтор события блокируется
и при выборе другой даты после рестарта. Ответ MAX с ошибкой/таймаутом,
потеря ответа и отсутствие message_id не разрешают повторную отправку.
Ошибка/отсутствие хранилища блокирует отправку. После аварии `lock` может
остаться: проверить журнал и группу вручную; не удалять резервы ради повтора.
Повреждённый журнал не восстанавливается автоматически.

Голоса и владение сообщениями остаются в памяти. После рестарта старый
опрос не восстанавливается, его кнопки игнорируются, повторная публикация
на ту же дату запрещена. Удаление старого сообщения оператор выполняет
вручную: бот не получает права удалять произвольные сообщения. В живом
экземпляре остаются две кнопки, список имён и закрытие/удаление в 22:00
МСК даты тренировки. Автопланировщик сохраняет окно 10:00–22:00 МСК.
Ручная команда допускается до этого окна и для будущей тренировки.
