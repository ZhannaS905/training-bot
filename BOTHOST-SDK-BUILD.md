Official documentation:

- https://bothost.ru/docs/custom-dockerfile — custom Dockerfile requires an
  explicit setting; a file in Git alone does not select it.
- https://bothost.ru/docs/common-errors — `/app` may be mounted from the host;
  copying node_modules from the image can disagree with a nonstandard layout.
- https://bothost.ru/docs/main-file-entrypoint — root manifest/entrypoint
  matters for autogenerated builds; custom Dockerfile uses CMD/ENTRYPOINT.
- https://docs.npmjs.com/cli/v11/using-npm/scripts/ — lifecycle hooks depend on
  installation options and are skipped by `--ignore-scripts`.
- https://nodejs.org/docs/latest-v22.x/api/modules.html#loading-from-node_modules-folders
  — a nested CommonJS require searches parent node_modules directories.

## Minimal candidate

Add `firebase: 12.19.0` to root production dependencies. Root lockfile reuses
the exact package versions, URLs and integrity values from the existing nested
lockfile. No dependency upgrade, loader change, start-command change or hook.
The existing createRequire anchored at `direct-sdk/package.json` finds
`/app/node_modules/firebase` after trying the nested location. A missing or
empty nested node_modules is harmless. A stale populated nested SDK would take
precedence and must be diagnosed by resolved paths rather than ignored.

This supports root npm ci/install in an autogenerated build, and the existing
custom Dockerfile's root npm ci. It avoids reliance on the platform recursively
installing nested manifests. It still requires BotHost to expose root
node_modules at runtime; it cannot repair a broken copy/mount mechanism.

Alternatives considered:

- postinstall/prepare running nested npm ci: fails with ignore-scripts, may run
  before nested files are copied, and does not fix nested artifacts being hidden.
- startup npm ci: runtime write permissions already fail; adds network and
  install work to every start. Not used.
- workspaces/file dependency: adds layout/hoisting assumptions without benefit
  for a single SDK; root dependency is sufficient.
- custom build command: no supported per-bot build-command field or current
  command was verified. Do not invent a bothost config file or change settings.
- custom Dockerfile only: nested installation already exists there. Changing
  it alone cannot establish SDK availability in the runtime `/app` tree.

Root SDK increases installed size. Existing Dockerfile retains its nested
installation for compatibility, so that path now installs two copies; both are
locked to the same graph. Removing the nested installation is deferred until
the actual deployment layout is verified. No dependency is initialized merely
by installation; normal bot entrypoints and direct safety flags are unchanged.
Do not deploy this branch to the main/production bot.

- Real `firebase/app`, `firebase/auth`, `firebase/firestore` imports via the
  unchanged nested createRequire: root paths, SDK_VERSION 12.19.0, empty nested
  node_modules. No initializeApp/authentication/database calls.
- Full Node 22 suite: 166 passed, zero failed/skipped.
- New regressions cover matching locked graphs and nested-to-root resolution
  with absent and empty nested node_modules, independent of working directory.
