# Training Bot

Расписание тренировок и опросы MAX с кнопками **✅ Приду / ↩️ Отменить**.
Каждый участник имеет один голос по user_id, может изменить или отменить его. В сообщении идут дата, место, время и нумерованный список записавшихся. Старые ответы «Возможно» и «Не приду» сохраняются в данных и поддерживаются обработчиком старых кнопок, но не входят в список записавшихся. Имена экранируются для HTML; идентификатором остаётся user_id.
Личных подтверждений, текстовой записи/отмены, помощи и создания опросов участниками нет.
Архив `logs/` сохранён и не используется новым приложением.

## Расписание

Часовой пояс — **Europe/Moscow**, независимо от часового пояса сервера.

| Дни | Начало | Место |
| --- | --- | --- |
| Пн, ср | 20:00 | мкр. Заря |
| Вт, чт | 18:30 | Поле чудес |
| Сб, вс | 18:00 | Яндекс Телемост |
| Пт | Нет тренировки и опроса | — |

Места и ссылка Телемоста сохранены из исходного кода; перед выпуском проверить их актуальность.
Автоматическая публикация — в **10:00** в день тренировки для явно заданных `CHAT_IDS`.
Проверка запускается каждую секунду после завершения предыдущей. Если приложение было выключено в 10:00,
оно создаёт пропущенный опрос при запуске в тот же день до начала тренировки. После начала и за прошлые дни не публикует.
Ручная команда `/опрос` — только от `ADMIN_IDS`, только в `CHAT_IDS`, на сегодня до начала тренировки.
Ручной опрос до 10:00 подавляет автоматический повтор. `/расписание` доступно участникам в разрешённом чате и отвечает там же.

## Изолированная проверка

Нужен Node.js 22 или новее. Внешних npm-зависимостей нет; package.json и lock-файл согласованы.

```sh
npm ci --ignore-scripts
npm test
```

Тесты используют временные каталоги и подмену MAX API. Один тест открывает локальный порт 127.0.0.1.
Импорт модулей не запускает приложение и не выполняет сетевых запросов.

Только для отдельного тестового бота: скопировать `.env.example` в `.env`, заполнить тестовый токен,
ID администратора, тестовые чаты и случайный `WEBHOOK_SECRET` (16–256 символов A–Z, a–z, 0–9, `_`, `-`).
Выделить отдельный постоянный `STATE_DIR`, не `logs/`, и выполнить `npm start`.
Не использовать токен действующего бота даже для проверки.

Приложение слушает `127.0.0.1:8080/webhook`. Для тестового окружения нужен HTTPS reverse proxy на порту 443
с доверенным сертификатом, который передаёт POST и заголовок `X-Max-Bot-Api-Secret`.
Подписку MAX на `message_created` и `message_callback` с этим секретом настраивает оператор отдельно;
приложение **не создаёт и не меняет подписки**, не меняет список команд бота.
До отдельного разрешения рабочие подписки и инфраструктуру не менять.

## MAX API и TLS

Использован небольшой REST-адаптер на встроенном fetch вместо устаревшей SDK-зависимости
(в main package.json требовал ^0.3.1, а lock фиксировал 0.2.1).
Актуальный хост `https://platform-api2.max.ru`, токен только в заголовке `Authorization`,
создание через POST `/messages`, изменение через PUT `/messages?message_id=...`.
Схема ответа создания: `message.body.mid`. Пересылка сообщений не используется для обновления опроса.
Редактирование/отправка ограничены общим интервалом 550 мс.
Сетевые запросы имеют тайм-аут 15 секунд; перенаправления запрещены.

TLS-проверка включена, запуск с `NODE_TLS_REJECT_UNAUTHORIZED=0` запрещён.
При необходимости настроить `NODE_EXTRA_CA_CERTS` с проверенным сертификатом доверенного CA;
не отключать проверку сертификатов. Реальные запросы MAX в рамках рефакторинга не выполнялись.

Документация, проверена 21.10.2026:
- [Создание сообщений](https://dev.max.ru/docs-api/methods/POST/messages)
- [Редактирование сообщений](https://dev.max.ru/docs-api/methods/PUT/messages)
- [Webhook и секрет](https://dev.max.ru/docs-api/methods/POST/subscriptions)

## Данные и сбои

`STATE_DIR/state.json` содержит опросы по паре chat_id/московская дата, UUID опроса, message ID,
голоса и отображаемые имена по user_id, журнал обработанных событий и устойчивую очередь Webhook.
Файл пишется через временный файл, fsync, атомарное переименование и fsync каталога.
Webhook подтверждается после записи события, обработка — последовательно.
Повторная доставка команды/кнопки не должна создавать повторный эффект.
Кнопка действует только при совпадении чата, сегодняшней даты, UUID и message ID.
Старые кнопки исходной версии игнорируются.

Перед отправкой опроса сохраняется резерв публикации. При тайм-ауте, сбое или отсутствии message ID
статус остаётся `pending`/`uncertain`, повторный POST автоматически запрещён.
Это обеспечивает защиту от дубликатов ценой возможного пропуска. Абсолютная гарантия «ровно один раз»
без идемпотентного ключа MAX невозможна. Оператор должен сверить чат, найти сообщение по UUID в payload кнопки
и при остановленном новом экземпляре привязать его mid и статус `published`; если публикации точно нет,
только после проверки можно удалить соответствующий резерв. Всегда сначала сделать копию state.json.
Не удалять резерв на основании одного тайм-аута. Создание замены при ошибке редактирования запрещено:
голос сохраняется, `dirty` остаётся до успешного повторного PUT.

Поддерживается один процесс и один локальный постоянный диск. Второй процесс блокируется каталогом `.lock`.
После аварийного завершения каталог не удаляется автоматически: оператор проверяет отсутствие процесса,
сохраняет резервную копию состояния и только затем убирает `.lock`. Не использовать NFS или несколько реплик.
Ошибка записи блокирует дальнейшие подтверждения событий; требуется проверка диска и перезапуск нового экземпляра.
Журнал событий и голоса автоматически не очищаются; нужны резервные копии, контроль размера и отдельная политика хранения.
Данные старого процесса из памяти автоматически не восстанавливаются и архивные JSON не импортируются.
