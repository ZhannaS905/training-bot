## Добавленный путь

fitpp-notification-test.cjs -> исходный createPreviewSession -> createSender ->
существующий MaxApi.send. Отдельная явная команда; основной entrypoint не меняется.
Первое чтение — только baseline. Исторические операции не отправляются.
Только demo-client-1, существующая включённая binding, bot 131384398,
личный chat 126619382 / user 5819064. Перед каждой попыткой проверяются GET /me
(включая username), GET /chats/{id}, type=dialog, status=active и dialog_with_user.
Не прошедшая проверку пара никогда не получает POST /messages.
Общие TEST_ALLOW_SEND/EDIT/DELETE и AUTO_PUBLISH должны оставаться false.
Сообщение явно помечено ТЕСТ, notify=false, без имён и контактных данных.

Дедупликация: атомарный exclusive create + fsync файла и каталога ДО POST.
Каталог /app/data/fitpp-notification-attempts-v1 должен находиться на сохраняемом
томе BotHost и быть доступен процессу node. Не удалять его при публикации.
Хранятся SHA256 ключи операций; при ошибке/таймауте попытка остаётся занятой.
Это at-most-once: возможна потеря уведомления при сбое после резерва, а не дубль.
Автоматический retry запрещён; uncertain требует ручной сверки MAX.
Лимит — 3 попытки за запуск процесса. Повторный запуск не снимает резервы.
Унаследованное ограничение детектора: пропуск attendanceRevision и неоднозначные
пакетные изменения не обрабатываются с догоняющей отправкой.

1. Опубликовать изменения только в feature/training-test-autopost, собрать только
   Training Test. Dockerfile включает новый standalone entrypoint, CMD прежний.
2. Проверить текущий серверный код, тестовые env (без вывода токенов), сохранность

3. Из /opt/training-test выполнить с имеющимися переменными и CA:

   node fitpp-notification-test.cjs --verify

   Ожидается FITPP_NOTIFICATION_VERIFIED no_send no_firestore_write.
   Эта команда читает два фиксированных документа fitpp-test и MAX identity/chat.
   При отказе остановиться, не менять IDs в коде ради обхода проверки.
4. Проверить dry-run:

   node fitpp-notification-test.cjs --watch

5. Только после успешной живой проверки и подтверждения сохраняемого тома
   запустить один отдельный ограниченный тестовый watcher:

   node fitpp-notification-test.cjs --send --watch

   Сделать новое синтетическое списание в fitpp-test, проверить результат sent,
   сообщение в подтверждённом личном диалоге и отсутствие дубля. Завершить Ctrl-C.
   Не воспроизводить старые списания специально для отправки.

Для отката остановить только этот watcher. Основной бот работает прежней командой.
Не удалять журнал попыток и не менять Firestore для отката.

## Подключение существующего preview watcher к подготовленной отправке

В `fitpp-notification-preview.cjs` добавлен явный режим `--send --watch`.
Он вызывает уже подготовленный `fitpp-notification-test.cjs`, который использует
исходный детектор, дисковую дедупликацию и существующий `src/api.js: MaxApi.send`.
Нового транспорта, второго цикла наблюдения или изменений основного бота нет.

Причина прежнего FITPP_PREVIEW_ONLY: после session.check выполнялся только
console.log; отправщик из preview вообще не вызывался. Теперь для нового режима
выполняется переход к готовому sender. Без --send прежний preview остаётся
полностью read-only. --send без --watch и сочетания с --checks/--diagnose запрещены.
Общие TEST_ALLOW_SEND/EDIT/DELETE и AUTO_PUBLISH остаются false. CHAT_IDS не меняется.

После отдельного согласования публикации и серверного включения существующий
watcher можно будет запустить с `--send --watch` вместо `--watch`.
Эта запись не означает разрешение запуска: в текущей работе команда отправки
на сервере не выполнялась. Перед включением нужны проверка текущего контейнера,
персонального диалога, сохраняемого /app/data и отсутствие параллельного watcher.
Сохраняются ограничения: только новый последовательный attendanceRevision,
первый снимок без отправки истории, синтетический клиент demo-client-1,
user 5819064, bot 131384398, chat 126619382, максимум 3 попытки за запуск.
При uncertain автоматического повтора нет; журнал попыток сохраняется при откате.
