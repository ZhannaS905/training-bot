## Порядок привязки

1. Сначала независимо установить MAX user_id владельца FitPP-Test: через проверенный владельцем аккаунт или доверенный канал администратора. Не использовать первого запустившего бота, ADMIN_IDS, пользователя группового опроса, имя, номер чата или deep link как доказательство. В коде нет автоматического источника такой проверки: это обязательная процедура оператора перед включением.
2. Сверить /me с существующей строгой проверкой Training Test. Только после успешной проверки создаётся обработчик.
3. Подготовить OWNER_DIALOG_ENABLED=true, OWNER_DIALOG_APPROVAL=fitpp-test-owner-approved, OWNER_DIALOG_USER_ID (проверенный независимо), OWNER_DIALOG_CODE_SHA256 (SHA256 случайного 16-байтового кода в hex), OWNER_DIALOG_EXPIRES_AT (Unix ms, максимум 10 минут вперёд), OWNER_DIALOG_STATE_DIR (канонический абсолютный путь отдельного постоянного каталога 0700, доступного процессу node). Секретный код передать только владельцу по доверенному каналу, без URL/deep link, логов и репозитория. Здесь код не создавался и реальные ID не записывались.
4. После отдельного разрешения на тестовое подключение сохранить текущую подписку и параметры rollback; сохранить все существующие update_types, добавить bot_started и message_created, сохранить тот же URL и проверку X-Max-Bot-Api-Secret. Не заменять список только новыми событиями. GET /updates не использовать: он может потреблять события параллельно webhook.
5. Владелец запускает бота и отправляет в его личный диалог `/confirm-owner <код>`. bot_started хранит лишь временного кандидата, игнорирует payload. Привязка требует того же отправителя и chat_id, chat_type=dialog, recipient.user_id=проверенный бот, свежие временные метки и правильный код. Пересланные сообщения, группы и каналы не подходят. Если событие запуска уже было раньше, сначала проверить штатный способ повторного bot_started; не останавливать бота автоматически.
6. Запись owner-dialog.json создаётся атомарно, 0600, с fsync. Один файл закрепляет одного владельца и один чат; другая привязка не перезаписывает его. Повторная доставка той же привязки допустима. При рестарте неподтверждённый кандидат теряется, нужен новый запуск. Истёкшее окно блокирует привязку, но не работу группового моста после перезапуска. Ошибка хранения возвращает retryable отказ webhook. Пять неверных кодов закрывают попытки до перезапуска; код имеет 128 бит энтропии.
7. subscriptionNotifications=false всегда. Файл не подключён к отправке уведомлений. Успех привязки проверять по безопасным признакам без вывода файла и персональных ID. Ни ответ-подтверждение, ни тестовое сообщение автоматически не отправляются.
