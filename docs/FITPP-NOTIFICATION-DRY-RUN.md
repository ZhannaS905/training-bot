# FitPP → Training Test: только dry-run

Отдельная команда читает Firebase Auth/Firestore REST. Она не импортирует бот,
MAX SDK или обработчики опросов, не запускает HTTP listener, webhook, планировщик
опросов или отправитель. Код отправки MAX и записи Firestore отсутствует.
`BOT_TOKEN` ей не нужен. Изменений окружения BotHost не требуется.

## Сборка и запуск

Dockerfile сохраняет Node.js 22, зависимости и их lock-файлы, TLS/CA, USER,
все ENV и `CMD ["node", "/opt/training-test/direct-training-test.cjs"]`.
Добавлен только COPY отдельного CLI; src уже копируется целиком.
`.dockerignore` теперь разрешает включение CLI. Указанный в панели
`bothost-test.cjs` не заменяет CMD собственного Dockerfile.

После отдельного разрешения на применение этой ветки **нужна пересборка
контейнера**. Этот PR не переключает работающую ветку и не выполняет деплой.
В консоли уже работающего тестового контейнера можно выполнить:

```sh
node /opt/training-test/fitpp-notification-preview.cjs
```

Команда читает оба документа, проверяет структуру и печатает
`FITPP_DRY_RUN_BASELINE_OK`, затем завершается. Это не подтверждение доступности
MAX или готовности привязки к отправке.
Для сравнения последующих чтений нужна отдельная явная команда:

```sh
node /opt/training-test/fitpp-notification-preview.cjs --watch
```

Для терминала BotHost, показывающего вывод после завершения команды:

```sh
node /opt/training-test/fitpp-notification-preview.cjs --checks 4
```

Это четыре проверки: baseline сразу и ещё три с паузами 30 секунд.
После четвёртой проверки процесс завершается с кодом 0 (около 90 секунд
плюс время запросов). Ошибка прерывает команду с ненулевым кодом и безопасным
`FITPP_DRY_RUN_FAILED ...`. Вывод baseline/check/preview сохраняется.
`--checks N` принимает положительное безопасное целое; `--checks 1`
эквивалентен обычному однократному запуску. Совмещать с `--watch` нельзя.
Поведение неограниченного `--watch` сохранено.

GET выполняется каждые 30 секунд последовательно. Первый снимок — baseline в
памяти процесса; далее `FITPP_DRY_RUN_CHECK_OK previews=N` и, только при
подтверждённом подходящем изменении, `FITPP_PREVIEW_ONLY remaining=5`.
Ctrl+C останавливает только CLI. Не запускайте второй экземпляр бота.
Baseline и множество уже наблюдавшихся operationId хранятся только в RAM;
после перезапуска первый снимок снова baseline, исторические операции не выводятся.
Не требуется и не разрешается в рамках этого PR создавать списание в Firebase.

## Firebase и границы доступа

Используются только `FIREBASE_API_KEY`, `FIREBASE_BOT_EMAIL`,
`FIREBASE_BOT_PASSWORD`. Сервисных/административных ключей нет.
Email/Password Auth — POST к accounts:signInWithPassword; все обращения
Firestore — GET к двум фиксированным документам проекта `fitpp-test`:

- `fitppTestWorkspaces/synthetic-v1/states/main`;
- `fitppTestWorkspaces/synthetic-v1/notificationBindings/training-test`.

Другой FIREBASE_PROJECT_ID отклоняется. UID, aud/iss/sub/exp полученного
ID token проверяются до Firestore GET; Firebase проверяет сам токен при GET.
Auth API key сам определяет проект авторизации: при ошибочном ключе запрос
sign-in может быть отклонён или вернуть чужой scope; такой токен не используется.
Ответ Firestore должен содержать точное имя документа вместе с проектом.
Редиректы запрещены, тайм-аут 15 секунд, токен обновляется повторным входом
через 45 минут. Никакие значения секретов/документов не логируются.
401/403/404, невалидный JSON, сеть, чужой проект/UID, неизвестная схема или
привязка останавливают CLI с безопасным кодом ошибки. Отсутствующие данные не
подменяются успешным baseline. Существующие Firebase Rules и права аккаунта
не меняются; права записи у этого аккаунта могут оставаться, но CLI их не использует.

## На чём проверена структура

Проверка не опирается только на новые фикстуры PR:

- `direct-core/FitPP-Test/persistence.js`: `read`, `reduce`, `sessionAction`,
  `attendance`. `clients` — массив, `subscriptions` — массив клиента;
  `visits[workoutId][clientId]` — строка статуса;
  `visitOps[workoutId][clientId]` содержит status/location/operationId,
  subscriptionId при списании абонемента; sessionAction добавляет workoutId.
  Списание делает `sub.left--`, отмена возвращает занятие и удаляет отметку.
  Денежное посещение может содержать moneyChargeId и исключается.
- `direct-core/fixtures/main.json`: документ synthetic-v1, ownerUid,
  schemaVersion=1, _fitppRevision и начальные карты. Это репозиторный снимок,
  **не доказательство текущего содержимого живого Firestore**.
- `src/contact-linking.js` (`validateRegistry`, `firebaseStore`) и
  `docs/CONTACT-LINKING.md`: документ `{version:1, botId, bindings:[...]}`,
  строки clientId/maxUserId/maxChatId/notificationsEnabled. Создание привязки
  использует `notificationsEnabled:false`. CLI не включает этот флаг.

Пилот намеренно допускает ровно одну привязку утверждённого demo-client-1 и
известного Training Test получателя. При `notificationsEnabled:false`, пустом
реестре, другой личности или нескольких привязках — previews=0. Не следует
изменять Firebase ради прохождения проверки. Формат реестра проверяется даже
на первом чтении; baseline OK не означает enabled-привязку.

## Детектор

Требуются последовательные attendanceRevision (+1) при неизменной _fitppRevision, новый уникальный operationId,
новая отметка attended, соответствующие visits/visitOps/workout,
существующий уникальный subscriptionId в обоих снимках и уменьшение left
**ровно на 1** при сохранении условий абонемента. Допускается штатное
bookingThaw.consumed=true. Архив, денежное посещение, изменение старой отметки,
отмена, дублированный/ранее наблюдавшийся ID, неоднозначные изменения других
посещений того же клиента и пропущенные revisions не дают предпросмотра.
После неоднозначного чтения baseline продвигается без догоняющих уведомлений.
Новое списание после отмены с новым ID допускается; повтор старого ID в том же
процессе исключается. Неизвестная структура завершает проверку безопасно.

Это консервативное сравнение снимков, а не очередь доставки. Между чтениями
можно пропустить операции; нет устойчивой истории через перезапуск. Никаких
гарантий доставки, реальной отправки или автоматического включения уведомлений.

## Проверки и ограничения

При подготовке базового dry-run: 22/22 специализированных теста и 215/215 полного набора в Node.js 22,
в контейнере с `--network none`, подменённой точкой входа `npm test` и без
реальных секретов. Включён тест с реальным reducer из bundled FitPP, отмены,
повторов, пропущенных revisions, структуры, отключённой привязки, Auth и
Firestore ошибок, чужого проекта, неизвестных аргументов и очистки логов.
Docker build и проверка включённых файлов/синтаксиса выполняются отдельно;
для них основной CMD бота не запускается. Существующий CI повторяет тесты; Docker build проверен локально.
Workflow оставлен прежним: текущее GitHub-подключение не имеет workflow scope.

Живые документы Firebase, доступность notificationBindings из BotHost и
текущая настройка работающего контейнера этим изменением не проверялись.
BotHost, ENV, ветка работающего Training Test, webhook, production, main и
данные Firebase не менялись. PR не объединять и не развёртывать без отдельного
разрешения. Не включать уведомления и не отправлять сообщения MAX.

### Проверки ограниченного режима `--checks`

28/28 специализированных тестов и 221/221 всех тестов прошли локально
(Node.js 24). Node.js 22 проверяется существующим GitHub Actions workflow.
Новые тесты подтверждают четыре снимка и три паузы по 30000 мс, ровно один

от неверных/совмещённых аргументов и прежний неограниченный `--watch`.
Отдельный запуск CLI с подменёнными Firebase-ответами и ускоренными тестовыми
таймерами проверяет фактические exit code 0/1, итоговый stdout и безопасный

пересборка или деплой BotHost не выполнялись.

## Диагностика previews=0

После пересборки Training Test из этой ветки выполните одну команду в BotHost:

```sh
node /opt/training-test/fitpp-notification-preview.cjs --diagnose --checks 4
```

Разделители команд и heredoc не нужны. Команда завершится примерно через
90 секунд; для первоначальной проверки ничего списывать не нужно.
`--diagnose` также совместим с `--watch` и однократным запуском.
Без флага прежний stdout сохраняется.

Дополнительные строки `FITPP_DRY_RUN_DIAGNOSTIC` содержат только ревизии,
boolean bindingApproved, количества всех visitOps/attendanceOps и visitOps
пилотного клиента, а также фиксированные коды причин с количествами.
Идентификаторы, имена, контакты, даты тренировок, значения полей операций,
токены и пароли не выводятся. `beforeAttendanceRevision:null` и `BASELINE_ONLY` означают
первый снимок. На последующих чтениях `ATTENDANCE_REVISION_NOT_PLUS_ONE` означает как
пропуск ревизий, так и отсутствие изменений: сравните beforeAttendanceRevision/afterAttendanceRevision.
Поля beforeRevision/afterRevision по-прежнему показывают _fitppRevision;
MAIN_REVISION_CHANGED блокирует смешанные или посторонние изменения.
Равные ревизии в спокойной базе нормальны и не доказывают причину прошлого
списания. Исторический before после завершения старого процесса недоступен.

Другие причины: BINDING_NOT_APPROVED (включая неверную личность/число
привязок даже при notificationsEnabled:true), NO_PILOT_VISIT_OPS,
NOT_ATTENDED, OPERATION_FIELDS_INVALID, OPERATION_ALREADY_IN_BEFORE,
DUPLICATE_OPERATION_ID, EXISTING_VISIT_OR_CORRECTION, MONEY_CHARGE,
WORKOUT_MISMATCH, SUBSCRIPTION_MISSING_AMBIGUOUS_OR_ARCHIVED,
SUBSCRIPTION_TERMS_CHANGED, OTHER_CLIENT_VISITS_CHANGED,
AMBIGUOUS_SUBSCRIPTION_BATCH, BALANCE_NOT_MINUS_ONE и OPERATION_SEEN_IN_SESSION.
Для каждой видимой операции выводится первый отказ её цепочки проверок;
диагностический режим продолжает проверку операций даже при отказе общей
привязки или ревизии, но предпросмотры по-прежнему запрещены этими условиями.
Baseline и защита от повторов продвигаются по прежним правилам.

Проверено: 31/31 профильных и 272/272 всех тестов на локальном Node.js.
Firebase/MAX подменены в тестах. Firestore writes, MAX, main, production,
Dockerfile, CMD и настройки BotHost не изменены; деплой не выполнялся.
Числа выше относятся к предыдущему этапу диагностики; текущая проверка описана ниже.


## Исправление контракта посещений — 26 октября 2026

Детектор использует только `attendanceRevision`: целое безопасное число >= 0,
строго +1. Отсутствующий счётчик означает 0, как в Pilot и сохранённых rules;
null/строка/дробь/отрицательное значение отклоняют документ. `_fitppRevision`
должна сохраняться. Запасного пути через её увеличение нет. При пропуске,
откате или смешанном изменении предпросмотр запрещён, baseline продвигается,
наблюдавшиеся ID запоминаются без догоняющих уведомлений.

Основание: Attendance.confirm атомарно сохраняет attendanceRevision,
attendanceReceipts и результат reducer. Сохранённые rules разрешают эти поля
и запрещают _fitppRevision в attendance write. Текущие опубликованные rules
не считывались и не менялись. ID квитанции — request.operationId, а ID в visitOps
создаёт reducer; это разные ID. Детектор проверяет новый уникальный visitOps ID,
связанный workout/subscription и точное изменение left на -1. Прежние проверки
привязки, статуса, отмен, коррекций, денег, условий абонемента и повторов сохранены.

Обновление выполняется только после отдельного согласования деплоя: сохранить
версию/образ для отката, выбрать ZhannaS905/training-bot и ветку
feature/training-test-autopost только у Training Test, пересобрать образ.
Это не просто перезапуск: CLI копируется Dockerfile в /opt/training-test.
Не менять CMD/ENV для запуска наблюдения и не запускать direct-training-test.cjs
вручную: штатный runtime не является read-only проверкой и содержит MAX-пути.
Пересборка также перезапускает штатный runtime, поэтому требует согласования.

После обновления выполнить в терминале Training Test:

```sh
node /opt/training-test/fitpp-notification-preview.cjs --diagnose --checks 4
```

Ожидаются baseline, три последующие проверки, bindingApproved:true и числовые
beforeAttendanceRevision/afterAttendanceRevision. В спокойной базе одинаковые
ревизии, ATTENDANCE_REVISION_NOT_PLUS_ONE и previews=0 нормальны. Это подтверждает
чтение и работу наблюдателя, но не end-to-end распознавание нового облачного
списания. До подтверждения этих логов повторное списание не выполнять.
HTTP_403/404, BINDING_NOT_APPROVED или STATE_REFUSED требуют разбора; не менять
rules/привязку и не повторять списание ради обхода отказа. Для длительного
наблюдения команда поддерживает --diagnose --watch, остановка Ctrl+C.

278/280; два loopback-теста получили listen EPERM. Оба файла повторены
