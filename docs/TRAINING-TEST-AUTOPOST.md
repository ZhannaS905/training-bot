Подготовлено на основе `origin/feature/fitpp-notification-dry-run`, SHA

`training-bot` и `notification-review` не изменялись. Точка входа остаётся

## Поведение

Ежедневная проверка с интервалом 1000 мс. Публикация при пересечении 10:00
`Europe/Moscow` работающим процессом, в пределах минуты 10:00. Если процесс
запущен после 10:00 или пропустил всю минуту, догоняющей отправки нет.
Пятница пропускается; прошлые даты никогда не публикуются.

| День | Место в существующем шаблоне | Время МСК |
|---|---|---|
| Понедельник | Заря | 20:00 |
| Вторник | Поле чудес | 18:30 |
| Среда | Заря | 20:00 |
| Четверг | Поле чудес | 18:30 |
| Пятница | — | — |
| Суббота | Яндекс Телемост | 18:00 |
| Воскресенье | Яндекс Телемост | 18:00 |

Используется существующая `body()` из `src/memory-training-test.js`.
Две кнопки: «✅ Приду», «↩️ Отменить». Дата без года, место/время жирным,
существующая ссылка Telemost, пустой список «🤨 Пока никто не записался!»,
непустой — «✅ Записано (N):» с нумерацией. По уточнению пользователя
разделители и длительность не добавляются. Сами функции оформления не менялись.

Новые опросы сохраняют голоса, callback receipts и порядок событий на том же
постоянном диске, что и журнал отправки, до ответа 200 вебхуку. Изменение
сообщения выполняется следующим tick (1000 мс), а фактическая задержка также
зависит от MAX. Неудачные PUT повторяются с фиксированным безопасным логом.
Отмена удаляет участника из списка, а не сообщение. На старте после перезапуска
сохраняются UUID, mid, голоса и флаг ожидающего редактирования. Голосование
закрывается через 60 минут после начала тренировки (как у текущего pilot).

Новые плановые опросы используют локальный список участников; они **не создают
бронирования и не списывают занятия в FitPP**. Существующий exact-poll маршрут
FitPP, его голосование, синхронизация и контактные сообщения сохраняются.
Новые опросы не регистрируются в Firebase и не расширяют pilot policy.
Снята только зависимость запуска ежедневного планировщика от срока закрытия
исторического pilot poll; проверки срока голосования этого pilot остаются.
Файлы уведомлений, dry-run, Firebase-подключение и тестовые документы не менялись.

## Безопасность и хранение

Общие `AUTO_PUBLISH`, `TEST_ALLOW_SEND`, `TEST_ALLOW_EDIT`, `TEST_ALLOW_DELETE`
остаются `false`. Новое отдельное разрешение создаёт только опросы в
`-80345864298680`, группа «Тест тренировок». Перед отправкой и редактированием
повторно проверяются `/me` (ID, `is_bot`, фиксированный username Training Test),
группа и членство бота. Перед PUT проверяются автор сообщения, группа, mid и
обе callback-кнопки с ожидаемым UUID. DELETE не предоставлен.
Токен передаётся заголовком, используется `platform-api2.max.ru` и существующий
доверенный сертификат. TLS-проверки не отключаются.

Хранилище — совместимый `Store`: эксклюзивная блокировка, временный файл,
fsync файла, atomic rename, fsync каталога. Сначала сохраняется `reserved`, затем
однократно вызывается POST. Ошибка, timeout, неполный ответ или сбой сохранения
успеха никогда не разрешают повторный POST. `reserved`/`uncertain` блокируют
автоматическую и ручную отправку на дату, в том числе после перезапуска.
Это приоритет отсутствия дубликатов: при сомнении возможен пропуск опроса,
требующий проверки человеком. Автоматического сброса журнала нет.

Папка журнала должна находиться на **реальном постоянном томе BotHost**,
общем для всех экземпляров этой тестовой сборки, и быть доступной пользователю
`node`. Флаг `TRAINING_TEST_AUTOPOST_DURABLE_VOLUME=true` — явное подтверждение
проверенного оператором тома, а не автоматическое обнаружение его типа.
Если у BotHost нет гарантированно сохраняемого тома, включать функцию нельзя.
Корневую ФС контейнера и временный диск использовать нельзя.

Отсутствующий, испорченный или заблокированный журнал останавливает запуск;
новый пустой журнал автоматически не создаётся. После аварийного завершения
может остаться `.lock`: сначала убедиться, что старый процесс завершён,
сохранить копию журнала, проверить MAX и только затем вручную убрать именно
оставшийся пустой lock-каталог. Сам журнал не удалять и не инициализировать заново.

## Установка — только после разрешения пользователя

1. Сверить новую голову исходной ветки с `855ac07`. Если работа PR #3 продвинулась,
   сначала перенести только коммит автопостинга на её актуальную голову в
   отдельной ветке и повторить тесты. Не объединять PR #3 или main.
2. Опубликовать подготовленную ветку `feature/training-test-autopost` в GitHub
   (`git push origin feature/training-test-autopost`) и выбрать её для сборки
   **существующего** сервиса Training Test в BotHost. Рабочий бот не менять.
3. До запуска подготовить/проверить постоянный том. Пример ниже предполагает,
   что `/app/data/training-test` уже существует на таком томе и доступен `node`.
   В новом образе, с тем же томом, выполнить **только один раз** от `node`:

   ```sh
   node /opt/training-test/training-test-autopost-state.cjs init /app/data/training-test/autopost-v1 2026-10-26
   ```

   Команда локальная, без MAX/Firebase; откажет при уже существующем каталоге.
   Перед первоначальной установкой проверить историю тестовой группы: если
   помимо встроенного pilot уже есть опросы на другие будущие даты, их нужно
   сначала учесть в журнале отдельной проверенной миграцией. Не запускать с
   пустым новым журналом вместо потерянного старого.
4. Сохранить все действующие переменные Firebase, FitPP, webhook, contact linking,
   токен и ожидаемый ID тестового бота. Не менять режимы уведомлений. Добавить:

   ```dotenv
   TRAINING_TEST_AUTOPOST_ENABLED=true
   TRAINING_TEST_AUTOPOST_DURABLE_VOLUME=true
   TRAINING_TEST_AUTOPOST_STATE_DIR=/app/data/training-test/autopost-v1
   TEST_ADMIN_IDS=<числовой MAX ID администратора или список через запятую>
   AUTO_PUBLISH=false
   TEST_ALLOW_SEND=false
   TEST_ALLOW_EDIT=false
   TEST_ALLOW_DELETE=false
   ```

   Новый путь должен отличаться от старого `STATE_DIR`; не использовать его
   для чужого состояния. Секреты не вставлять в команды и журналы.
5. После разрешённой сборки и запуска проверить `/health`: `ready=true`,
   `autopostEnabled=true`. Существующий `pollDisplayReady` относится к pilot
   FitPP, а не к журналу автопостинга. Существующая подписка MAX должна доставлять
   `message_callback`; для ручной команды также `message_created`. URL и секрет
   вебхука не меняются. Изменять подписку, если потребуется, только отдельно
   согласованным действием.

## Проверка после установки

Запуск до 10:00 МСК: дождаться 10:00 в свободный тренировочный день, увидеть
один опрос по расписанию. Запуск после 10:00: сообщений не должно появляться.
Для явной ручной публикации **сегодняшней свободной даты**, до начала тренировки,
администратор из `TEST_ADMIN_IDS` пишет в тестовой группе:

```text
/тестопрос-сегодня
```

Дата параметром не принимается, чужие чаты и неадминистраторы отвергаются,
устаревшие команды не исполняются. Повтор команды после успеха или неопределённого
результата ничего не отправит. **Команда в этой работе не запускалась.**

Проверка журнала без вывода персональных данных:

```sh
node /opt/training-test/training-test-autopost-state.cjs status /app/data/training-test/autopost-v1
```

После `published` должен быть один mid на дату. При `external` используется
существующий pilot, при `reserved`/`uncertain` требуется ручная сверка истории
MAX, повторной отправки нет. Команда status показывает снимок, не меняет файл.
После штатного перезапуска повторить status и команду администратора: mid
сохраняется, второго сообщения нет. Проверить «Приду», повторное нажатие,
«Отменить», обновление имён, затем штатный перезапуск и сохранение списка.
Не проверять отказоустойчивость удалением журнала или повторным init.

Для отключения: `TRAINING_TEST_AUTOPOST_ENABLED=false` и штатный перезапуск,
сохранив журнал. Без автопостинга возвращается исходное ограничение запуска
по сроку исторического pilot poll. Код и настройки уведомлений не откатывать.

## Проверки разработчика

Полный набор запускается `node --test test/*.test.js` на Node 22 (как в Docker).
Новые проверки используют только моки MAX, локальные временные файлы и
поддельный SDK; нет сетевых запросов к MAX/Firebase, записей Firestore,
деплоя или ручной публикации. Проверяется общий авторизованный webhook,
маршрутизация в существующий FitPP и контакты, durable receipt до 200,
все дни/границы времени, ручная команда, рестарты, потеря ответа MAX,
потеря записи успешного результата, хранение голосов и повторные PUT.
Часовой пояс проверяется дополнительными запусками с `TZ=UTC` и
`TZ=America/Los_Angeles`.

Официальные источники MAX, сверенные при работе:
https://dev.max.ru/docs-api/methods/POST/messages и
https://dev.max.ru/docs-api/methods/GET/me.

Результат окончательного прогона: Node 22.23.4 — 240/240 тестов; отдельные
прогоны новых тестов при TZ=UTC и TZ=America/Los_Angeles — по 18/18.
`git diff --check` без ошибок. Docker-образ и живые сервисы не запускались.
